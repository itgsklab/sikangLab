你可能已经用大模型写过邮件、改过代码，却仍然好奇：如果要自己做一个真正能用的 AI 产品，究竟该学什么？答案不是把所有新名词背一遍，而是沿着一个问题往前走——怎样让模型在真实任务中，给出有依据、可执行、可检查的结果？

[LLM-Master](https://github.com/youngyangyang04/llm-master) 是一个面向有编程基础读者的中文学习仓库。它把内容排成“全局认知 → 模型调用 → RAG → Agent → 生产工程 → 原理与面试”的路径。下面借这条路线，用一个“公司内部知识助手”的例子，解释每一步究竟在解决什么问题。本文是基于仓库目录与路线的原创导读，不是对全部教程的逐篇摘要。

## 第一站：先让模型稳定地回答

最简单的 AI 应用，是把用户的问题发给模型，再把回答显示出来。但“能回答”离“能交付”还差一截：回答格式可能变化，请求可能超时，输入太长会增加成本。于是，开发者需要学会设计提示词、约束输出结构、处理错误、记录用量，并让长答案逐步显示出来。这些能力构成了模型调用的基本功。

以知识助手为例，第一版可以只做一件事：用户输入问题，系统返回一段清晰的回答。别急着加功能，先确认它在正常、模糊、无关和失败请求下分别会怎样表现。

## 第二站：让回答找到依据——RAG

如果用户问“公司的报销上限是多少”，模型未必知道这家公司的最新制度。仅靠提示词要求它“不要编造”，也不能凭空补上缺失的信息。RAG（检索增强生成）因此登场：先从可信文档中找出相关片段，再连同问题一起交给模型回答。

这里的难点并不只是“接一个向量数据库”。文档怎样切分、候选材料怎样召回、相关性怎样重排、答案如何附上引用，都决定了结果是否可靠。更重要的是准备一组固定问题来评测：答案对不对？引用能否支持结论？找不到资料时会不会坦诚说不知道？仓库把切片、Embedding、混合检索、Rerank、引用和评估放在同一条链路里，正是为了让知识库从演示走向可检验的系统。

## 第三站：让系统采取行动——Agent

知识助手能回答“报销规则是什么”，但如果用户说“帮我查这笔报销的状态，并提醒审批人”，系统就需要调用工具、读取状态，可能还要等待外部结果。这类任务进入了 Agent 的范围：模型不再只生成文字，而是在明确的权限和流程边界内，决定下一步该调用什么工具。

这也意味着风险升级。查错记录、重复发送提醒、工具超时后再次执行，都会影响真实业务。因此，一个实用的 Agent 不能只有“会调用工具”：还应有清晰的工具契约、运行记录、权限限制、失败恢复和评估方式。仓库的 Agent 阶段特别强调可追踪、可中断、可评估，而不是把“自主”当作唯一目标。

## 第四站：让它在真实流量下工作

哪怕前三步都跑通，一上线仍可能遇到高峰期响应变慢、模型服务失败、费用超预算等问题。生产工程要处理的是这些“不理想但一定会发生”的情况：超时与重试、限流与监控、部署与缓存、性能测试和容量规划。一个漂亮的 Demo 证明想法可行；一份记录延迟、成本、错误与恢复方案的报告，才更接近系统可用。

Transformer 原理、微调和模型部署也在仓库中占有位置，但不必一开始就全部学完。如果目标是做应用，可以先把“调用—检索—行动—运行”做成一个闭环，再根据瓶颈回头补原理：检索不准就研究数据与评估，延迟过高再研究推理与部署，任务确实需要改变模型行为时再考虑微调。

## 给初学者的一个可执行顺序

先做一个带错误处理和用量记录的问答页面；再加入几份真实文档，让每个回答都能指向依据；接着只开放一个低风险工具，例如查询某条记录的状态；最后，用一组固定测试问题和失败场景反复检查。每走完一步，都问自己三个问题：它解决了什么真实需求？怎样证明效果变好了？出错时如何收场？

大模型应用开发的主线，并不是追逐最多的新术语，而是逐层缩小“模型会说”和“系统可信”之间的距离。LLM-Master 的价值，正在于把这段距离拆成了可以学习、实践和验证的阶段。它尤其适合已有编程基础、想转向大模型应用或 AI 后端的读者；若目标是基础模型研究，还需要另外补充更深入的算法与数学材料。
